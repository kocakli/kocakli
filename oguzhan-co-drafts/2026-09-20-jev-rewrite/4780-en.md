Three question types. That is the Jev API surface you need to learn.

**Choice** picks from a closed list. **Score** places an input on ordered levels. **Noul** estimates the probability that a yes/no proposition is true. Put those questions beside some `state`, send one request, and TypeSafe's System One model returns values your code can use without scraping labels from prose.

[The hub post](https://www.oguzhan.co/typesafe-jev-system-one-decision-model/) covered the larger TypeSafe argument. Day 1 stays close to the request: how to define a question, how the answer types differ, and why one call with several questions is usually better than a row of tiny calls.

## Start with one snap judgment

The most important line in the [primitives documentation](https://docs.typesafe.ai/primitives) is not a field name. It is the instruction to ask for one judgment a knowledgeable person could make quickly from the supplied evidence.

“Does this message request a refund?” fits.

“Analyze the customer's history, decide what happened, choose the best remedy, and draft a response” does not. That job contains evidence gathering, policy interpretation, a decision, and text generation. Split it. Let code connect the parts.

Every Jev question has:

- an **ID**, such as `refund_requested`, used to find the answer in your program;
- a **type**, one of `choice`, `score`, or `noul`;
- **instructions** containing the full judgment to make;
- and, where needed, **criteria** defining the options or levels.

The ID is not sent to the model. A neat variable name does not rescue vague instructions. Write the complete question.

## Choice: one route from a known map

Use Choice when the allowed answers form an unordered closed set.

Support routing is the obvious example: `billing`, `technical`, `sales`, or `other`. Document type, programming language, and request intent work the same way. The model chooses one option and returns its probability distribution over all of them.

Choice answers contain:

- `choice`: the selected key;
- `probabilities`: a probability for every supplied option;
- `confidence`: a summary of how peaked the distribution is.

Coverage is your responsibility. If real input can fall outside the list, add `other` or `none_of_the_above`. Without an escape option, the model must select the least-wrong item you gave it.

Choice maps cleanly to a `switch`. That is its strength.

## Score: a position on levels you define

Use Score when the answer lies on a spectrum and each part of that spectrum has a meaning you can write down.

Bug severity, customer frustration, account risk, and demonstrated skill are Score-shaped. The criteria are ordered levels, not unrelated labels. Jev returns a numeric position along those levels, and that position may sit between two named points.

Score answers contain:

- `score`: the position on the scale;
- `legend`: the numbered levels you supplied;
- `probabilities`: the distribution across those levels;
- `confidence`: the peakedness summary.

Weak rubrics make weak scores. “Low, medium, high” leaves most of the work hidden. “Cosmetic issue,” “workflow blocked with workaround,” and “data loss or security exposure” gives the model and your reviewers something testable.

Scores map to ranges and thresholds in code. Define those thresholds from labeled examples, not from the pleasing shape of one response.

## Noul: probability of yes

Noul is for a crisp proposition:

- Does the message contain PII?
- Is the customer asking for a refund?
- Does the resume say the candidate used Python at work?

The answer has one field, `noul`, between 0 and 1. Near 1 means strong probability of yes. Near 0 means strong probability of no. A value around 0.5 means the model is split.

It does not mean “medium.”

That distinction catches many bad question designs. “How skilled is this candidate in Python?” is a Score. “Does the resume show professional Python use?” can be a Noul, provided the criterion is explicit.

Noul has no separate confidence field. The probability is the signal.

## One state, three questions

A request may mix all three types. Here is the shape using TypeSafe's Python SDK:

```python
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

state = {
    "ticket_message": "My flight was cancelled. Can I get a refund?",
    "refund_policy": "Cancelled flights qualify for a full refund.",
}

with TypeSafeClient() as client:
    response = client.system_one(
        state=state,
        questions={
            "request_type": Choice(
                instructions="What is the main request in `ticket_message`?",
                criteria={
                    "refund": "The customer wants money returned.",
                    "rebooking": "The customer wants another flight.",
                    "information": "The customer only wants information.",
                },
            ),
            "frustration": Score(
                instructions=(
                    "How frustrated does the customer appear "
                    "in `ticket_message`?"
                ),
                criteria=[
                    "Calm and neutral.",
                    "Concerned but civil.",
                    "Very angry or using strong language.",
                ],
            ),
            "refund_requested": Noul(
                instructions="Does `ticket_message` request a refund?",
            ),
        },
    )
```

The state goes once. Each question sees it, runs independently, and returns under the ID your application chose.

Independence has two consequences. Adding a question does not turn its answer into hidden context for the others. Removing one should not poison the rest. It also means a later question cannot see an earlier result inside the same request.

If question B genuinely depends on answer A, make another call after code receives A. Real dependencies include fetching new evidence, rebuilding the state, or choosing B's allowed options. If both questions can be answered from the original state, send them together.

## Point to the exact field

Production state is rarely a single sentence. It may contain a ticket, order, refund policy, account history, and internal notes.

When a question should inspect one part, name its dot-and-index path inside backticks:

```text
Does `ticket.messages[0].text` request a refund?
```

Or:

```text
Does `refund_policy` cover the duplicate charges in `order.charges`?
```

Those paths are instructions to the model, not code executed against the object. They remove ambiguity about which slice matters. Clear paths also make the question easier for a human to review later.

## Batch questions before reaching for another call

System One evaluates questions in parallel. If several questions use the same state, put them in the same request and mix types as needed.

The TypeSafe parallel-questions cookbook measured 13 questions over one large document. In the source snapshot behind this post, one batched request was reported as roughly **11.5 times cheaper** and **9.6 times faster** than 13 sequential calls, with the answers unchanged. The current cookbook can move as the model and cached runs are refreshed, so keep the version and run data with any number you quote.

The cost explanation is simple. A long document sent once is cheaper than the same document sent 13 times. Sequential network round trips add latency too. If you fire 13 requests concurrently, the wall-clock difference narrows, but the repeated input bill remains.

This leads to TypeSafe's **speculative fan-out** pattern: ask every independent question the program may need, even when some answers will be ignored for a particular input.

A support request might include:

- a Choice for department;
- a Noul for refund intent;
- a Score for frustration;
- a Score for bug severity;
- a Noul for PII.

If the request is not a bug, discard the severity answer. A few question tokens are usually cheaper than another state upload and another round trip.

Coding agents often default to one question per tool call. That habit is expensive here.

## Compose decisions in code

Jev questions should remain small. The workflow can still be complex because application code combines the answers.

Suppose ticket priority depends on business impact, customer frustration, and evidence quality. Ask three Score questions. Normalize their answers, assign weights in code, and compute priority there. When the support team changes its policy, adjust the weights rather than hiding a new policy inside a longer prompt.

The same rule applies to gates:

```python
if refund_requested > 0.85 and policy_match > 0.90:
    queue_for_refund_review()
else:
    send_to_human()
```

Those numbers are illustrative, not defaults. Thresholds should come from your own labeled cases and the cost of each error.

## The answer can be valid and wrong

Jev will keep a Choice inside the list. It can select the wrong item in that list. A Score can overrate an angry-looking phrase. A Noul can put 0.9 on a false reading.

Before an irreversible tool call:

- validate on production-like data;
- measure false positives and false negatives;
- keep deterministic policy checks;
- preserve an escalation path;
- pin the model and provider version.

The clean output shape is an interface guarantee. It is not an audit certificate.

That is the useful reading of Jev's primitives. Choice gives your program a branch. Score gives it a position. Noul gives it a probability. Your code supplies the policy around all three.
